VAHAN Registration Pipeline

A plain-language account of how Flow 1 (Vahan_StateMonthwise) pulls monthly vehicle-registration data from the Government of India's VAHAN portal — every state, broken down by manufacturer — without anyone sitting at the screen, and how it checks its own work before handing over the files.

Why this exists

The Sales & Marketing team uses VAHAN registration numbers for market share, fuel-trend and planning work. Getting them by hand means logging in, setting the same filters, solving a picture-code, running a report and downloading a file — then repeating that 36 times (once per State/UT), on a daily cadence.

This automation does exactly what the person did, in the same browser, on the same public page — just unattended. It also adds a step a person rarely has time for: it independently re-checks that the 36 downloaded files add up to the national totals before anything is delivered.

Source: the public analytics.parivahan.gov.in/analytics/vahanpublicreport page — the same one staff already use. No login, no paid API, nothing leaves the machine.

1–9End-to-end flow

One run = setup, then the same four actions repeated for each of the 36 states, then packaging and the accuracy check. Roughly 4–5 minutes start to finish.

  1. 1

    Trigger

    Someone clicks Start run on the dashboard, or a scheduled Windows task starts it (the PDD asks for daily). Nothing to babysit.

  2. 2

    Open a browser

    The tool launches Chromium (Chrome's engine) in the background and opens a fresh, private session — its own cookies, its own captcha.

  3. 3

    Go to the VAHAN report page & set the fixed filters

    It waits for the page to load (retries up to 3× if the site is down), then applies the same six filter settings every time — see The filters.

Repeats for each of the 36 States / UTs
  1. 4

    Pick the state

    From Andaman & Nicobar to West Bengal. The portal's own state code (MH, KA, DL…) is read straight from the page and becomes part of the file name.

  2. 5

    Solve the captcha

    The page shows a distorted code. The tool reads it automatically; if it isn't confident, the dashboard shows the image and a person types it in. Full detail in The captcha.

  3. 6

    Run the report

    Clicks Apply. The portal reloads with the manufacturer × month table for that state.

  4. 7

    Download & rename the Excel

    Clicks Download All Records Excel, waits for the file, checks it isn't empty, and renames it to the standard convention.

    Monthwise_2026-MH.xlsx Monthwise_2026-KA.xlsx … (36 files)
  1. 8

    All-India reference file

    After the 36 states, it selects all states together and downloads one national file. This is only used for the accuracy check and is deliberately kept out of the delivered zip.

  2. 9

    Package, check, summarise, close

    Zips the 36 state files → runs the reconciliation check → writes an Excel summary (states done, time taken, pass/fail) → closes the browser. Emailing the summary is the one piece still to be wired up.

    Flow1_StateMonthwise_2026_<timestamp>.zip + Flow1_Summary_<timestamp>.xlsx

2The filters — what the report contains

Six settings, identical on every state, every run. They decide the shape and scope of the report; the tool never changes them mid-run.

FilterValue usedWhy
Archived Flag All four: Active-Compliant, Active-Non-Compliant, Permanent Archive, Temporary Archive Count every registration, not only currently-active ones
Year Type Calendar Year → current year Report covers January to today of this year
Vehicle Sub-Category Light Motor Vehicle + Light Passenger Vehicle Passenger / light vehicles only — the segment the team tracks
Y-Axis (rows) Maker One row per manufacturer
X-Axis (columns) Month Wise One column per month

Behind the scenes these are ordinary form controls on the page (#archivedFlags, #vehicleSubCategory, #yAxis, #xAxis…). The tool sets them the same way a person would — it just does it in code, so a filter can never be forgotten or picked wrongly.

3How the captcha is handled

VAHAN asks for a fresh 6-character picture-code before every Apply — about 37 times per run. This is the part people expect to block automation, so it has four layers.

  1. A

    Read it automatically

    The tool screenshots the captcha image and runs it through ddddocr — a small open-source text-recognition model built for exactly this kind of code. It runs offline; the image never leaves the machine, and there is no paid captcha service.

  2. B

    Submit if the guess looks solid

    A plausible 5–8 character result is typed into the box and Apply is clicked.

  3. C

    Retry on a weak or rejected guess

    If the result looks off, or the portal rejects it, the tool requests a fresh captcha and tries again — up to 5 attempts per state.

  4. D

    Ask a person (dashboard runs)

    If automatic reading keeps failing, the run pauses and shows the captcha image in the dashboard. An operator types it and the run resumes exactly where it stopped. A 10-minute window applies before it falls back to another automatic attempt.

In the last full 36-state run: automatic reading solved 35 of 37 codes on the first try; the other 2 succeeded on the second attempt. No human input was needed.

4Where the data lives

There is no database. Results are plain files on one Windows machine, one folder per run, named by run-id and timestamp so nothing is ever overwritten.

│  └─ 1789015865-4_flow1_20260910-102105\   ← one folder per run
│     ├─ files\                              ← the 36 renamed state files
│     │  ├─ Monthwise_2026-AN.xlsx
│     │  ├─ Monthwise_2026-MH.xlsx  … (36 total)

│     ├─ Flow1_StateMonthwise_2026_*.zip     ← the deliverable (36 files)
│     └─ Flow1_Summary_*.xlsx                ← counts, timing, check result
├─ downloads\      scratch — where Chrome drops a file before renaming
├─ logs\           reserved for run logs
├─ calibration\    one-time snapshots of the portal's page layout
├─ config.yaml     all settings: URL, filters, retry counts, naming
└─ data\state_master.csv   the 36 state names + codes

The delivered zip holds exactly the 36 state files. The All-India file sits beside it for the accuracy check but is never included, per the PDD. The summary spreadsheet records how many states were processed, how long it took, and whether the check passed.

5Sessions — three kinds, all short-lived

  • BrowserA fresh private Chromium profile per run. Holds the portal's cookies and the current captcha. Created at the start, closed at the end — nothing is reused between runs, so one run can never disturb another.
  • Run stateLives in memory in the dashboard while a run is active. Its progress bar, live log and any pending captcha. One run at a time. Cleared if the dashboard is restarted — but the output files and summary on disk are permanent.
  • Portal (their side)VAHAN ties each captcha to its own server session cookie. Our browser session carries that cookie, which is why a fresh browser per run avoids stale-captcha problems.

6The accuracy check (PDD Step 8.2)

Collating 36 separate files risks something going missing or being counted twice. The check removes the doubt for two manufacturer groups the team follows.

  • Group MBMercedes-Benz · Mercedes-Benz AG · Mercedes-Benz India Pvt Ltd · Daimler AG

The tools, in one line

Python drives a real Chrome browser (via Playwright); a small web app (FastAPI) is the dashboard; an offline model (ddddocr) reads the captchas; Excel files are read and written with openpyxl. It all runs on one Windows machine — no cloud, no external services, no paid APIs.
